## Как думают ИИ

ИИ мыслят горизонтальными слоями (отдельно реализовать backend, отдельно frontend, отдельно bd), но это не очень эффективно, так как правки могут быть массивными и это сложней тестировать.

Поэтому лучше покрывать все вертикальными фазами, которые будут затрагивать все касающиеся того или иного аспекта моменты за одну фазу.

## Если использовать для implement более слабую модель, а на review более сильную, то можно получить более качественный результат на выходе.

Это хорошо сочетается с двумя фазами кода (см. п. 1 в «Перед началом проекта»): слабая модель пишет код до Green, сильная на ревью приводит его к стандартам.


## Как начать проект с нуля:
1) описать идею ИИ, дать все возможные вводные данные и пообщаться с ним на эту тему. Дать позадавать ему вопросы и предложить решения / улучшения (можно через grill). Можно сохранить все рассуждения и идеи в документы по типу research.md.
2) prototyping, чтобы была еще более ясная картина того, что я хочу получить.
3) описать User Experience и Agent Experience (feedback loops, technology choice, module shape, testing strategies).
4) сгенерировать примерный дизайн приложения.
5) завести `CODING_STANDARDS.md` (см. раздел ниже) и сослаться на него из `CLAUDE.md`.

## Стандарты кода: CODING_STANDARDS.md

Стандарты написания кода живут в отдельном файле `CODING_STANDARDS.md`. В `CLAUDE.md` на него ссылаются через импорт: `@CODING_STANDARDS.md`. Его же использует ревью на соответствие стандартам (п. 11 ниже).

Содержимое — в файле `CODING_STANDARDS.md` в корне репозитория: простота, SOLID, Encapsulation, выбор простого решения, форматирование (Prettier как пример).

## Перед началом проекта описать ИИ:
(стандарты кода — в `CODING_STANDARDS.md`)

0) термины:
	- spec — описание одной фичи или этапа с требованиями.
	- тикет — вертикальная часть spec (БД + backend + frontend одного аспекта). Делается в отдельной ветке и worktree.
	- пакет — все тикеты одной spec.

1) код пишется в две фазы:
	а) implementation: просто пиши код, который покрывает тесты и переводит их из Red в Green. Этот код не обязан соответствовать `CODING_STANDARDS.md`, но остаётся простым и понятным, без запутанности.
	б) refactor: после автоматического ревью пакета (п. 11) приведи код к `CODING_STANDARDS.md`, не усложняя там, где это не нужно. Рефакторинг делается один раз на пакет, отдельным коммитом `refactor:`, не смешивая с коммитами Green.
Так эффективнее, чем требовать стандарты сразу: модель не отвлекается от поведения и тестов, а правки по стандартам делаются осознанно и в одном месте.

2) во время работы над тикетом запускай тесты затронутого кода и стражи (п. 8). Стражи быстрые и запускаются всегда. Полный прогон (все тесты проекта) делай только по явной команде или в конце пакета.

3) тесты пиши на согласованных seams (местах, где проверяется поведение) через публичный интерфейс: HTTP API, публичные методы модулей. Моки — только на границах системы. Через тот же интерфейс (например, MockMvc / @SpringBootTest) обязательно проверяй:
	- права доступа, включая вызовы без прав;
	- формат ошибок;
	- валидация и граничные случаи;
	- контракты API.
Не дублируй тестами на разных уровнях то, что уже покрыто на согласованном seam.

4) ручное тестирование — отдельный тикет для пользователя, создаётся только по явной команде пользователя. Сам, по своей инициативе, такой тикет не создавай и не предлагай включить его в разбивку. Если пользователь явно попросил, при разбивке spec на тикеты последним создай тикет, в котором описан план тестирования проделанной работы: явные шаги ручной проверки приложения по всему пакету. Этот тикет не выполняется агентом, зависит от всех остальных тикетов пакета и закрывается человеком. После завершения пакета предложи пользователю приступить к нему.

5) при разделе spec на тикеты, он должен делиться на "вертикальные" тикеты, а не горизонтальные. Так код легче будет потом тестировать, а один тикет будет затрагивать все касающиеся того или иного аспекта моменты за один прогон. Исключение: тикет для пользователя (п. 4), если его явно запросили, — он один и последний.

6) параллельные тикеты веди в отдельных worktree, одна ветка на тикет. Изменения в общих местах выноси в отдельный базовый тикет. Он сливается до старта параллельных тикетов. Общие места — это:
	- схема БД и миграции;
	- общие DTO и API-контракты;
	- общие модели и сервисы.
В каждом тикете укажи:
	- что он меняет;
	- что может только дополнять;
	- что ему запрещено менять;
	- от каких тикетов он зависит.
Если нужны чужие схема или интерфейс, которых нет в контексте, остановись и запроси контекст (NEEDS_CONTEXT).

7) в репозитории должен быть скрипт живой проверки, например scripts/live-check.sh. Он делает следующее:
	- запускает приложение с профилем, близким к боевому;
	- подключает реальные зависимости (БД и т.д.);
	- прогоняет сценарии из spec;
	- сравнивает результат с ожидаемым, описанным в spec.
Код выхода 0 — только если все сценарии совпали.
При найденном дефекте:
	а) тест, воспроизводящий дефект. Он падает.
	b) исправление. Тест проходит.
	c) если дефект относится к целому классу ошибок, добавь страж (п. 8).

8) стражи — это архитектурные тесты (например, ArchUnit), которые запускаются при каждом прогоне. На каждый класс багов — свой страж. Обязательные стражи:
	- У каждого метода @RestController с маппингом есть @PreAuthorize. Публичные эндпоинты (логин, health и т.п.) перечислены в явном списке исключений.
	- В @Service-классах нет публичных final-методов (они ломают Spring-прокси: @Transactional и т.п.).
	- Секреты не попадают в ответы: контроллеры не возвращают entity напрямую, а DTO ответов не содержат полей вроде password/token/secret.
Для каждого нового стража сначала покажи, что он падает на намеренном нарушении. Приложи вывод.

9) Раздел «Готово, когда» в шаблоне плана. Для каждого тикета:
	- Для тикетов, меняющих поведение: тест сначала падает, затем проходит, и есть вывод обоих запусков. Для тикетов без изменения поведения (рефакторинг, конфиг): затронутые тесты проходят до и после.
	- Для новых и изменённых эндпоинтов проверены права (в том числе запрос без прав) и формат ошибок.
	- В ответах нет секретов (стражи проходят).
	- Сборка завершается с кодом 0.
Для пакета:
	- Каждое требование spec связано с тестом или проверкой: ID требования указан в имени или описании теста.
	- Ручные изменения сгенерированного кода занесены в файл generated-code-changes.md в хранилище артефактов (вне репозитория): файл, что изменено, почему.
	- Рефакторинг по `CODING_STANDARDS.md` выполнен отдельным коммитом `refactor:` (п. 1), после него тесты зелёные.
	- Если пользователь явно запросил тикет с планом ручной проверки (п. 4) — он создан.
	- Полный прогон (п. 2) и живой скрипт (п. 7) завершаются с кодом 0.

10) после обсуждения идеи выдай одним сообщением на одно согласование:
	- spec;
	- разбивку на тикеты (тикет для пользователя, п. 4, — только если его явно запросили);
	- полный план параллельной работы (если она есть / требуется).
Даже после согласования плана получи отдельное подтверждение пользователя перед необратимыми действиями:
	- слияние в основную ветку;
	- push;
	- удаление веток или worktree;
	- миграции на БД с реальными данными;
	- удаление файлов.

11) ревью:
	- каждый тикет перед слиянием проверяй через /code-review на баги;
	- соблюдение стандартов (`CODING_STANDARDS.md`) и соответствие spec проверяй один раз на весь пакет;
	- по находкам ревью пакета делай рефакторинг (п. 1б) одним отдельным коммитом `refactor:`;
	- тикеты, связанные с безопасностью (аутентификация, права, работа с секретами), проверяй на это дополнительно по каждому.

12) перед созданием первого worktree подготовь .gitignore. Одна ветка на тикет, других веток (временных, экспериментальных, копий) не создавай.
Перед слиянием проверь git log <base>..HEAD: в ветке должны быть только коммиты этого тикета. Сливай тикеты по одному, после каждого — сборка и тесты затронутого кода. После последнего слияния запусти полный прогон (п. 2) и живой скрипт (п. 7).
