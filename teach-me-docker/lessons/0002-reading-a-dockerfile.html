Читаем Dockerfile

Урок 2 из курса «Docker: читать чужие проекты и CI». Около 12 минут. Предыдущий: образ и контейнер.

Цель урока: открыть чужой Dockerfile и объяснить, что получится на выходе и почему строки идут именно в таком порядке.

Что такое Dockerfile

Это текстовый документ, по которому создаётся образ. В нём записано, какие команды выполнить, какие файлы скопировать, какую команду запускать при старте и так далее.[1] Иначе говоря, Dockerfile — рецепт, образ — результат, контейнер — запуск результата.

Восемь инструкций, которые вы встретите чаще всего

ИнструкцияЧто делает
FROMБазовый образ, который расширяет сборка
WORKDIRРабочая директория внутри образа, куда копируются файлы
COPYКопирует файлы с хоста в образ
RUNВыполняет команду во время сборки
ENVЗадаёт переменную окружения для запущенного контейнера
EXPOSEПомечает порт, который образ «хочет открыть»
USERПользователь по умолчанию для всех последующих инструкций
CMDКоманда по умолчанию, которую запустит контейнер

Описания по документации Docker.[1]

Разбираем настоящий пример

Это пример из официальной документации (Python-приложение):[1]

FROM python:3.13
WORKDIR /usr/local/app

# Install the application dependencies
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

# Copy in the source code
COPY src ./src
EXPOSE 8080

# Setup an app user so the container doesn't run as the root user
RUN useradd app
USER app

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]

Читайте сверху вниз как последовательность шагов:

  1. FROM python:3.13 — берём готовый образ с Python как основу.
  2. WORKDIR — дальше работаем в /usr/local/app.
  3. COPY requirements.txt и RUN pip install — ставим зависимости.
  4. COPY src ./src — кладём исходный код.
  5. RUN useradd app и USER app — приложение будет работать не от root.
  6. CMD [...] — при docker run стартует uvicorn на порту 8080.
Про RUN и CMD. RUN выполняется один раз при сборке образа и результат остаётся в образе. CMD выполняется при каждом запуске контейнера. Эту путаницу вы будете видеть в чужих проектах чаще всего.

Почему порядок строк важен

Каждая инструкция Dockerfile становится слоем образа.[2] Если слой изменился, его нужно пересобрать, а вместе с ним пересобираются все слои после него.[2]

Поэтому в примере зависимости (requirements.txt) копируются и ставятся раньше, чем исходный код: код меняется часто, зависимости редко. Страница о кэше прямо этого не формулирует, но её пример подразумевает именно такой порядок: то, что меняется реже, идёт раньше. Подробнее в разделе Build cache.

Сборка и теги

docker build -t my-image .

Точка в конце — контекст сборки: место, где сборщик ищет Dockerfile и файлы, на которые тот ссылается. Без -t образ получит только трудно запоминаемый ID.[3]

Полное имя образа выглядит так: [HOST[:PORT]/]PATH[:TAG]. Хост по умолчанию — docker.io, тег по умолчанию — latest. Поэтому docker/welcome-to-docker из прошлого урока — это то же самое, что docker.io/docker/welcome-to-docker:latest.[3]

Попробуйте в терминале

Создайте пустую папку, а в ней файл Dockerfile (без расширения) с двумя инструкциями из таблицы выше:

FROM python:3.13
CMD ["python", "-c", "print('hello from my image')"]

Образ python:3.13 скачается целиком при первой сборке, это может занять время. Затем:

docker build -t hello-py .
docker image ls                 # ваш hello-py в списке
docker run hello-py             # выведет приветствие
docker run hello-py             # снова: новый контейнер из того же образа
docker ps -a                    # оба запуска видны как контейнеры

Теперь добавьте между строк RUN echo "build step" и соберите ещё раз. Посмотрите на вывод сборки: что именно Docker делает заново, а что уже есть? Своими словами это «слои и кэш» из раздела выше.

Проверьте себя

1. Какая инструкция задаёт базовый образ?

FROM указывает базовый образ, который расширяет сборка. WORKDIR задаёт рабочую папку, а CMD — команду запуска.

2. Что произойдёт при docker run с образом из примера?

CMD — команда по умолчанию для контейнера. pip install выполнился один раз при сборке, а сборка — это отдельная команда docker build.

3. Вы изменили файл в src и пересобрали образ из примера. Что пересоберётся?

Изменённый слой и все слои после него пересобираются. Слои до COPY src (включая установку зависимостей) остаются прежними.

4. Что означает точка в конце docker build -t app .?

Точка — это контекст сборки: путь, где сборщик находит Dockerfile и нужные ему файлы.
