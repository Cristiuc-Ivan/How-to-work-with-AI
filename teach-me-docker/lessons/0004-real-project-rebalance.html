Разбор реального проекта: Dockerfile и app.yml из rebalance

Урок 4 из курса «Docker: читать чужие проекты и CI». Около 20 минут. Предыдущий: Docker Compose.

Цель урока: прочитать два настоящих файла из вашего проекта и объяснить, что из них собирается, что запускается и в каком порядке. Новых понятий здесь четыре: многоэтапная сборка, healthcheck, условия в depends_on и extends.

Сначала: как эти два файла связаны

Прежде чем читать построчно, полезно понять, что перед вами. Комментарии в файлах говорят об этом прямо.

  • Dockerfile — образ фронтенда (Angular, раздаётся через nginx). По комментарию в нём, он собирается сервисом frontend в Compose.
  • app.yml — Compose-файл бэкенда: сервис app запускает образ rebalance (по комментарию в Dockerfile, он собирается инструментом jib, не Dockerfile), рядом поднимаются PostgreSQL и Elasticsearch.
Наблюдение. В app.yml нет сервиса frontend, хотя Dockerfile ссылается на него. Значит, фронтенд описан в каком-то другом Compose-файле. Кроме того, postgresql.yml и elasticsearch.yml, на которые ссылается app.yml, в папке урока отсутствуют, поэтому их содержимое я не вижу. Это нормально: в чужих проектах картина почти всегда собирается из нескольких файлов.

Часть 1. Dockerfile

FROM node:24-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginxinc/nginx-unprivileged:1.28-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist/frontend/browser /usr/share/nginx/html
EXPOSE 8080

Новое понятие: многоэтапная сборка

В файле две инструкции FROM. Это многоэтапная сборка: в одном Dockerfile несколько этапов, у каждого своя база, и между этапами можно «выборочно копировать артефакты».[1] Этап можно назвать: AS build даёт первому этапу имя.[1] Смысл в том, что инструменты сборки остаются в ранних этапах, а в итоговый образ попадает только нужное.[1]

Этап 1: build (Node)

СтрокаЧто делает
FROM node:24-alpine AS buildБазовый образ с Node, этап называется build
WORKDIR /appДальше работаем в /app
COPY package.json package-lock.json ./Копирует только описание зависимостей
RUN npm ciСтавит зависимости строго по lock-файлу
COPY . .Копирует весь остальной код
RUN npm run buildСобирает Angular-бандл

Про npm ci: это «чистая установка» для автоматизированных окружений, включая CI. Ей нужен существующий package-lock.json; если lock не совпадает с package.json, команда падает с ошибкой, а node_modules перед установкой удаляется.[2]

Это урок 2 в действии. Сначала копируются только package*.json и ставятся зависимости, и лишь потом копируется весь код. Если изменить файл исходников, слои до COPY . ., включая npm ci, не пересобираются, потому что пересобираются изменённый слой и все после него.[3] Первое . в COPY . . — корень контекста сборки, второе — папка назначения внутри этапа.[4]

Этап 2: итоговый образ (nginx)

СтрокаЧто делает
FROM nginxinc/nginx-unprivileged:1.28-alpineНовая база: nginx; Node здесь уже нет
COPY nginx.conf /etc/nginx/conf.d/default.confКладёт ваш конфиг nginx из контекста сборки
COPY --from=build /app/dist/frontend/browser /usr/share/nginx/htmlЗабирает готовый бандл из этапа build
EXPOSE 8080Документирует порт 8080

COPY --from копирует из образа, этапа или именованного контекста вместо контекста сборки, а путь-источник считается от корня указанного этапа.[4] Здесь /app/dist/frontend/browser — папка, созданная npm run build на первом этапе. В финальный образ попадает только она, без Node и без node_modules.

Про EXPOSE: инструкция не публикует порт, она лишь документирует, какие порты слушает контейнер; публикуют их при запуске флагом -p.[4] Это тот же ports из Compose.

Три вопроса к этому Dockerfile

  1. Где CMD? В файле его нет. Документация говорит, что Dockerfile должен задавать CMD или ENTRYPOINT,[4] но прямо не пишет, что CMD наследуется от базового образа. Скорее всего, команду запуска nginx приносит базовый образ, но это моё предположение. Проверить можно командой из практики ниже.
  2. Почему порт 8080? Имя образа «unprivileged» намекает на запуск без прав root, но страница на Docker Hub не называет ни пользователя, ни порт.[5] Что слушает nginx на самом деле, задаёт ваш nginx.conf и базовый образ: сверьте.
  3. Актуальна ли база? На странице nginxinc/nginx-unprivileged написано, что репозиторий больше не поддерживается и нужно использовать nginx/nginx-unprivileged.[5] Это не ошибка сборки, но повод сказать команде проекта.

Часть 2. app.yml

Верхний уровень

  • name: rebalance — имя Compose-проекта. Проект группирует ресурсы и изолирует их от других развёртываний.[6] Из него получатся имена вроде rebalance-app-1.
  • Комментарий вверху: конфигурация для разработки, за усиление для продакшена отвечаете вы. Читайте такое буквально.
  • Три сервиса: app, postgresql, elasticsearch.

environment: что внутри

Переменные вида SPRING_DATASOURCE_URL — это настройки Spring Boot, а не Docker: Docker лишь передаёт их в контейнер. Обратите внимание на адреса jdbc:postgresql://postgresql:5432/rebalance и http://elasticsearch:9200. Хосты postgresql и elasticsearch совпадают с именами сервисов ниже в файле. Сервисы общаются через сеть Compose,[6] и это совпадение имён не случайно. Как именно имя сервиса работает как адрес, я в документации пока не разбирал (см. пробелы в RESOURCES.md).

SPRING_DATASOURCE_PASSWORD= оставлен пустым. Для образа PostgreSQL переменная POSTGRES_PASSWORD обязательна и не может быть пустой.[8] Что делает именно ваш postgresql.yml, я не вижу, поэтому вопрос открытый: где задаётся пароль базы и совпадает ли он с пустым паролем приложения.

ports: зачем 127.0.0.1

Формат — [HOST:]CONTAINER. Если IP не указан, Docker привязывает порт ко всем интерфейсам (0.0.0.0) и обходит правила файрвола хоста; указав 127.0.0.1, вы открываете порт только для самой машины.[7] Здесь так и сделано: API бэкенда виден только локально.

healthcheck

healthcheck объявляет проверку, по которой определяется, «здоров» ли контейнер сервиса.[7] test — команда проверки; CMD-SHELL запускает строку в оболочке контейнера по умолчанию.[7]

test:
  - CMD-SHELL
  - "bash -c 'exec 3<>/dev/tcp/127.0.0.1/8080; printf \"GET
    /management/health HTTP/1.0\\r\\nHost: localhost\\r\\n\\r\\n\" >&3;
    grep -q \"\\\"status\\\":\\\"UP\\\"\" <&3'"
interval: 5s
timeout: 5s
retries: 40

Прочитать это можно так (это моя расшифровка команды, не цитата из документации): bash открывает TCP-соединение на 127.0.0.1:8080 прямо из контейнера, отправляет HTTP-запрос на /management/health и ищет в ответе "status":"UP". Нашёл — контейнер здоров. Так сделано, чтобы не требовать в образе ни curl, ни wget. Проверка идёт каждые 5 секунд, с таймаутом 5 секунд и до 40 попыток: приложению даётся порядка трёх с лишним минут на запуск.

depends_on с условием

В уроке 3 был короткий depends_on: - db (только порядок запуска). Здесь длинная форма, которая позволяет задать дополнительные поля.[7] Условие service_healthy означает, что зависимость должна быть «здоровой» (по её healthcheck) до запуска зависимого сервиса.[7] То есть app стартует, только когда PostgreSQL и Elasticsearch прошли свои проверки. Это не то же самое, что «контейнер просто запущен» (service_started).

Сервисы postgresql и elasticsearch: extends

postgresql:
  extends:
    file: ./postgresql.yml
    service: postgresql

extends позволяет делить общие настройки между файлами и даже проектами; file — путь к Compose-файлу, service — имя сервиса, который берётся за основу.[7] Сервис наследует все свойства из указанного, и их можно локально дополнять или менять.[9] Поэтому настоящие образы и тома баз данных нужно искать не в app.yml, а в postgresql.yml и elasticsearch.yml.

Проверьте себя

1. Зачем в Dockerfile две инструкции FROM?

Это многоэтапная сборка: ранние этапы нужны для сборки, и их инструменты не попадают в итоговый образ. Копируются только нужные артефакты.

2. Что делает COPY --from=build?

--from меняет источник: вместо контекста сборки берутся файлы из указанного этапа, образа или именованного контекста.

3. Что означает 127.0.0.1:8080:8080 в ports?

С указанным IP 127.0.0.1 порт привязан только к локальной машине. Без IP Docker привязывает порт ко всем интерфейсам.

4. Что задаёт condition: service_healthy для postgresql?

Зависимость должна стать «здоровой» по своему healthcheck до запуска зависимого сервиса. Это строже, чем service_started.
