# CODING_STANDARDS

Стандарты написания кода. Применяются на фазе refactor (после автоматического ревью пакета), а не на фазе implementation: там достаточно простого кода, который переводит тесты из Red в Green. Рефакторинг не должен усложнять код там, где это не нужно.

1) Код должен быть простым и понятным, без излишних усложнений, где это не требуется.

2) При написании кода опирайся на SOLID:
	S — Single Responsibility: у класса одна причина для изменения.
	O — Open/Closed: код открыт для расширения и закрыт для модификации.
	L — Liskov Substitution: наследник подставляется вместо родителя без нарушения логики.
	I — Interface Segregation: несколько узких интерфейсов лучше одного широкого.
	D — Dependency Inversion: модули верхнего уровня зависят от абстракций, а не от модулей нижнего уровня.
SOLID применяй там, где он снижает связанность и упрощает изменения. Не вводи интерфейс или абстракцию, пока у неё нет второй реализации или конкретной причины (например, подмена в тестах). Если SOLID и п. 1 расходятся, приоритет у простоты.

3) Также не забывай про Encapsulation (is a principle where an object's internal state is hidden from external code).

4) Если требуется принять какое-то решение, то выбирай самое простое и эффективное из существующих. В будущем всегда можно усложнить какую-то функцию, а вот упростить тяжелей. Это же касается и предлагаемых вариантов — самое простое и эффективное из существующих.

5) Форматирование (пример правил для стека с Prettier; подставь свои):
	- Каждый файл форматируется Prettier с существующим `.prettierrc` репозитория (в корне и в `frontend/`). Настройки Prettier/EditorConfig не меняй, файлы, которые иначе не правишь, не переформатируй.
	- Форматируй только затронутые файлы: `npx prettier --write <files>` (во `frontend/` запускай из `frontend/`). Проверка: `npm run prettier:check` (корень) или `npm run format:check` (frontend).
	- Окончания строк оставляй те, что уже используются в репозитории (см. `.editorconfig`); CRLF/LF не конвертируй.
